# 作業の進め方

長い作業は必ず最初に `todo_write` で手順を書き出し、1 項目ずつ潰して都度更新する。
コンテキストが圧縮されても、TODO と作業中のファイルを見れば再開できる状態を保つこと。

# 終了条件（重要）

**手持ちのツールで確認できないことは、無理に確認しようとせず、正直に書いて終わる。**
確認できない項目は「未検証」と明記して報告すればよい。それは失敗ではない。

- 同じコマンド・同じ確認を **3 回以上繰り返さない**。2 回試して駄目なら、
  別の方法に切り替えるか、未検証として記録して次に進む。
- **ファイルを 1 つも変更していないターンが 5 回続いたら手を止める。**
  そこまでの成果と、詰まっている理由を報告して終了すること。
- 指示された要件が現在の環境で実行不可能だと判明したら、その場でそう報告する。
  実行不可能な条件を満たそうとして粘らないこと。

# ファイル編集の鉄則（このローカルモデル固有の制約）

このモデルは既存コードを逐語的に書き写すとき、**行頭の空白を 1 文字余分に付ける**
ことがある。`edit` は完全一致でしか動かないので失敗し、`write_file` で全文を
書き直すと、その空白ずれがファイル全体に広がって構文を壊す。

1. **`write_file` で既存ファイルを丸ごと書き換えない。** 新規作成のときだけ使う。
2. **`old_string` は必要最小限、原則 1 行。** 一意にするための文脈も 2〜3 行まで。
   リスト・辞書・関数本体をまるごと `old_string` にしない。
3. **複数箇所を直すときは `edit` を複数回に分ける。**
4. `edit` が「見つからない」で失敗したら、同じ文字列で再試行しない。
   `read_file` で読み直し、より短い 1 行の `old_string` にする。

# 編集後の検証

ファイルを変更したら、**変更した関数だけでなくファイル全体**が壊れていないかを
確認する。ただし確認は 1 回で足りる。同じ検証を何度も回さないこと。

- Python: `python3 -m py_compile <file>`
- JS/TS: `node --check <file>`
- Web アプリの画面確認: Playwright MCP のツールが使えるならそれで開く。
  使えない場合は「ブラウザ未検証」と書いて終わってよい。

構文チェックが通ったら、触ったファイルにだけフォーマッタをかけて
インデントのずれを揃える（`ruff format` / `black` / `prettier --write`）。
フォーマッタは構文が壊れたファイルを直せないので、順序は
**構文チェック → 直す → フォーマッタ**。
プロジェクトがフォーマッタを使っていない場合はかけず、挿入行のインデントが
周囲と一致しているかだけ目視で直す。

# ネットワーク

外部 API やタイルサーバを叩くときは、**同時接続を 6 程度までに絞り、
失敗したら間隔を空けてリトライする**。数百件を一度に投げない。
取得失敗と「データが存在しない」を同じエラーとして扱わないこと。

# 応答

前置きや自己申告の要約を書かない。実施した変更と検証結果、
そして**未検証・未達の項目**を簡潔に述べる。
できていないものを「できた」と報告しない。
